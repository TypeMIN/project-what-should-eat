# 01 — 계정과 로그인, 배포된 앱

## Outcome

배포된 주소에서 누구나 고유 ID·PIN·표시 이름·출생연도·성별로 가입하고, 그 ID와 PIN으로 다시 로그인할 수 있다. 로그인한 사용자는 자신이 로그인했음을 화면에서 확인할 수 있고, 로그아웃할 수 있다.

## Blockers

None. 첫 작업이다.

## Acceptance criteria

- [x] 배포된 공개 주소에서 앱이 열린다.
- [x] 새 사용자가 영문 소문자와 숫자로 된 고유 ID, 숫자 4~6자리 PIN, 표시 이름, 출생연도, 성별을 입력해 가입할 수 있다.
- [x] 가입 전에 ID 중복 여부를 확인할 수 있고, 이미 존재하는 ID로 가입을 시도하면 거부되고 이유가 표시된다.
- [x] 출생연도는 전체 연도 목록에서 선택하고, 성별은 남성/여성 버튼으로 선택한다.
- [x] 가입한 ID와 올바른 PIN으로 로그인하면 로그인 상태가 된다.
- [x] 틀린 PIN으로는 로그인되지 않고 이유가 표시된다.
- [x] 저장된 인증 정보에서 PIN 원문을 읽어낼 수 없다.
- [x] 로그아웃하면 로그인 상태가 해제된다.
- [x] 브라우저를 새로 고쳐도 로그인 상태가 유지된다.

## Constraints

- PIN은 숫자 4~6자리이며 평문으로 저장하지 않는다.
- ID는 영문 소문자와 숫자로만 구성한다.
- 못 먹는 음식은 가입 항목에 포함하지 않는다(스펙의 제외 영역).
- 이 작업이 배포와 데이터 저장소 준비를 함께 끝낸다. 이후 작업은 이미 살아 있는 주소 위에 올린다.

## Verification

- 배포된 주소를 열어 가입 → 로그아웃 → 같은 ID·PIN으로 재로그인이 성공하는 것을 확인한다.
- 같은 ID로 두 번 가입 시도 시 두 번째가 거부되는 것을 확인한다.
- 틀린 PIN으로 로그인 시도 시 실패하는 것을 확인한다.
- 저장된 사용자 레코드를 직접 조회해 PIN 입력값과 저장값이 다른 것을 확인한다.

누적 범위: 계정 생성·인증·세션 유지와 데이터 접근 경계 전체.

위험: 이후 모든 참가자 관계와 선택 이력이 이 신원 위에 쌓이므로, 인증 방식을 잘못 고르면 되돌리는 비용이 가장 크다. 특히 "고유 ID + PIN" 모델은 이메일+비밀번호를 전제하는 인증 서비스와 맞지 않아 갈림길이 있다 — 합성 이메일로 표준 인증을 쓰면 행 수준 접근 제어가 자연스럽게 따라오지만, 자체 세션을 만들면 "본인이 참여하지 않은 결정은 보이지 않는다"(작업 05)를 앱 코드로만 보장하게 된다. 이 선택과 그 결과를 사람이 한 번 확인한다.
