# 03 — 주변 음식점 후보 생성

## Outcome

참가자를 확정한 세션 진행자가 현재 위치를 쓰거나 지역을 검색해 기준 위치를 정하면, 그 주변 실제 음식점 중에서 규칙에 따라 추려진 최대 8개 후보를 받는다.

## Blockers

작업 02. 후보를 추리는 규칙이 오늘 참가자들의 최근 방문 이력을 쓰므로, 참가자 구성이 먼저 있어야 한다.

## Acceptance criteria

- [ ] 현재 위치 사용을 허용하면 그 좌표를 기준으로 후보가 만들어진다.
- [ ] 위치 사용을 거부하거나 실패하면 지역 검색 입력으로 이어지고, 검색해서 고른 지역으로 후보가 만들어진다.
- [ ] 두 경로 중 어느 쪽으로 기준 위치를 정해도 이후 후보 선정 결과의 형태가 같다.
- [ ] 후보는 더미 데이터가 아니라 실제 조회된 음식점이며, 이름·카테고리·거리를 확인할 수 있다.
- [ ] 후보에 술집과 간식(베이커리류) 카테고리가 없다.
- [ ] 오늘 참가자 중 누군가가 최근 7일 내 최종 선택한 곳은 후보에 없다.
- [ ] 후보가 8개보다 적게 남으면 있는 만큼만 제시되고, 2개 미만이면 A/B 선택으로 넘어가지 않고 조건에 맞는 곳이 부족하다는 안내가 표시된다.
- [ ] 같은 위치·같은 참가자로 다시 실행하면 후보 구성이 매번 동일하지는 않다.

## Constraints

- 음식점 조회는 기준 좌표에서 가까운 순으로 한다. 정확도순 기본값을 쓰면 후보가 실제로 가까운 곳이 아니게 된다.
- 조회 반경은 1km로 고정한다. 반경을 넓혀도 결과가 늘지 않는 것이 확인되었으므로 반경 확장으로 후보 부족을 해결하려 하지 않는다.
- 후보 풀은 조회로 얻은 거리순 상위 45곳 전체다. 별도로 상위 몇 곳을 더 자르지 않는다.
- 외부 API 키는 브라우저에 노출하지 않는다.
- 못 먹는 음식으로 후보를 거르는 규칙은 이번 범위에 없다.

## Verification

- 실제 좌표로 후보를 만들고, 반환된 후보의 카테고리에 술집·간식이 없는 것을 확인한다.
- 최근 방문 이력을 미리 넣어둔 상태에서 후보를 만들고, 그 장소가 빠지는 것을 확인한다. 이 이력은 작업 04가 만들지만, 이 작업에서는 이력 데이터를 직접 준비해 검증한다.
- 후보 풀을 인위적으로 1곳 이하로 줄인 상태에서 부족 안내가 뜨는 것을 확인한다. 실제 지역에서 후보가 8개 미만이 되려면 같은 45곳 안에 최근 방문 기록이 30건 넘게 있어야 해 자연 발생하지 않으므로, 완화 동작 자체는 별도로 재현하지 않는다.
- 위치 거부 상황에서 지역 검색으로 이어지는 경로가 동작하는 것을 확인한다.
- 브라우저로 오가는 요청에 외부 API 키가 실려 있지 않은 것을 확인한다.

## Review checkpoint

One review pass after this task.

누적 범위: 외부 음식점 조회와 후보 선정 규칙 전체, 그리고 그 결과가 참가자 데이터와 결합되는 방식.

위험: 외부 API의 응답 형태·정렬·개수 상한을 잘못 다루면 이후 모든 단계가 잘못된 후보 위에서 돌아가고, 화면상으로는 정상으로 보인다. 특히 정렬 기준을 지정하지 않으면 조용히 엉뚱한 45곳을 가져오는 것이 이미 확인되었다. 조회 결과가 실제로 가까운 곳인지, 제외 규칙이 실제로 적용되는지, 키가 노출되지 않는지를 사람이 한 번 확인한다.
