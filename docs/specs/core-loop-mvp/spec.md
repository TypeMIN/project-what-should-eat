# Core Loop MVP

## 목적

`PRODUCT.md`의 핵심 루프(로그인 → 참가자 선택 → 주변 탐색 → 후보 생성 → 세션 진행자의 A/B 선택 → 결과 저장 → 이력 조회)를 하루 강의 안에서 끝까지 도는 하나의 작업 단위로 완성한다. 개인화 학습, Food Profile, 그룹 궁합, 정교한 다양성 추천은 이번 범위 밖이며 이유는 아래 "제외 영역"에 있다.

## 사용자에게 보이는 결과

- 사용자는 영문 소문자와 숫자로 된 고유 ID와 PIN으로 가입하고 로그인한다.
- 로그인한 사용자는 ID 또는 표시 이름 검색으로 오늘 같이 먹을 사람을 참가자로 추가한다.
- 참가자를 확정하면 현재 위치, 또는 검색으로 고른 지역 주변 음식점 후보 여러 개를 받는다.
- 로그인한 세션 진행자가 후보를 둘 중 하나씩 골라나가면 마지막에 식당 하나가 남는다.
- 결정된 식당은 저장되고, 이후 아무 때나 로그인해서 지난 결정들을 목록으로 다시 볼 수 있다.

## 승인된 범위

0. **배포 가능한 앱** — Supabase 프로젝트와 배포를 갖춘 상태에서 시작한다. `PRODUCT.md`의 성공 신호 중 셋이 "배포된 앱에서"를 전제하므로, 배포는 마지막에 몰지 않고 첫 결과물부터 살아 있는 주소 위에 쌓는다.
1. **가입/로그인** — 영문 소문자와 숫자로만 된 고유 ID의 중복 여부를 확인하고, 숫자 4~6자리 PIN, 표시 이름, 전체 연도 목록에서 고른 출생연도, 남성/여성 선택 버튼으로 성별을 입력받는다.
2. **참가자 구성** — ID 또는 표시 이름 검색으로 오늘의 참가자를 추가·제거한다. 로그인한 본인은 항상 참가자에 포함되며 제거할 수 없고, 본인 혼자인 구성도 유효하다. 그룹 저장(자주 만나는 조합 재사용)은 포함하지 않는다.
3. **주변 음식점 조회** — 현재 위치 또는 검색으로 선택한 지역 기준으로, 기준 좌표에서 **가까운 순으로** 실제 음식점 목록을 가져온다. 두 경로 모두 같은 기준 좌표 하나로 이어져, 이후 규칙은 좌표가 어디서 왔는지 상관하지 않는다.
4. **후보 N개 선정** — 아래 "확정된 규칙"에 따라 자동으로 추린다.
5. **A/B 선택** — 로그인한 사용자가 세션 진행자로서 두 후보 중 하나를 고르는 승자 유지 방식으로 마지막 하나가 남을 때까지 반복한다.
6. **결과 저장** — 최종 식당, 참가자 전원, 결정 시각을 남긴다.
7. **이력 조회** — 로그인한 사용자가 자신이 참여했던 과거 결정을 볼 수 있다.

## 확정된 후보 선정 규칙

사용자 확인을 거친 규칙이며, 순서대로 적용한다. 출발점은 기준 좌표에서 가까운 순으로 가져온 음식점 목록이다.

1. `docs/decisions/food-category-taxonomy.md`에 따라 술집·간식(베이커리류) 카테고리는 제거한다.
2. 오늘 참가자 중 누구든 최근 7일 내 방문(=이전에 최종 결과로 선택)한 곳은 제거한다. 다만 이 조건까지 적용한 후보가 N개 미만이면, 채워질 때까지 최근 방문 조건을 완화한다.
3. 그래도 N개에 못 미치면 남은 후보를 있는 그대로 쓴다 — 억지로 채우지 않는다. 남은 후보가 2개 미만이면 A/B 선택 자체를 시작하지 않고 "주변에 조건에 맞는 곳이 부족하다"고 알린다.
4. 남은 곳에서 무작위로 N개(모자라면 있는 만큼)를 뽑는다.

이번 범위에서 **오늘의 참가자가 후보에 영향을 주는 경로는 규칙 2(최근 방문 이력) 하나뿐이다.** 개인 취향 학습이 범위 밖이므로, 참가자를 바꿔도 그 사람들의 최근 방문 기록이 다를 때만 후보가 달라진다.

## 확정된 제약과 근거

- 추천 후보는 한 끼 식사에 해당하는 곳으로 한정한다. 술집·간식은 제외한다(`PRODUCT.md`, `docs/decisions/food-category-taxonomy.md`).
- "동남아"는 카카오의 "아시아음식" 대분류 아래 중분류로 남아 있고, 이번 스펙은 이를 별도 대분류로 재구성하지 않는다(`docs/decisions/food-category-taxonomy.md`).
- 시스템은 최종 식당을 대신 결정하지 않는다 — A/B 선택은 항상 세션 진행자의 마지막 선택으로 끝난다(`PRODUCT.md`).
- PIN은 숫자 4~6자리이며 평문으로 저장하지 않는다.
- ID는 영문 소문자와 숫자로만 구성한다.
- 저장된 그룹과 오늘 참가자는 항상 구분한다(`PRODUCT.md`) — 이번 스펙엔 그룹 저장 자체가 없으므로 지금은 참가자 구성이 곧 오늘 참가자다.

## 가정

되돌리기 쉬운 선택이며, 문제가 보이면 언제든 바꿀 수 있다.

- 위치는 브라우저 Geolocation API로 가져오거나, 사용자가 지역을 검색해 기준 위치로 고를 수 있다(Phase 0에서 검증한 것과 같은 카카오 키워드 검색 방식). Geolocation을 거부·실패하면 검색 입력으로 유도한다. 좌표를 숫자로 직접 입력하는 화면은 두지 않는다 — 검색이 이미 그 역할을 대체한다.
- 후보 수 N은 8로 시작한다(7번의 A/B 선택으로 결정).
- 조회 반경은 1km로 고정한다. 카카오 카테고리 검색은 중심점당 최대 45건까지만 반환하므로(`size` 최대 15 × `page` 최대 3, 실측 확인), 반경을 넓혀도 더 많은 후보가 확보되지 않는다 — 1km와 2km가 동일한 45곳을 반환하는 것을 확인했다. 반경을 늘리는 완화 규칙은 두지 않는다.
- 후보 풀은 거리순 상위 45곳 전체다. 실측상 이 45곳은 도심에서 반경 130m 내(홍대입구 9~129m), 주거지역에서도 145m 내(방배역 45~143m)에 들어와 전부 도보권이므로, 따로 상위 몇 곳으로 더 자르지 않는다.
- "최근 방문"의 기준 기간은 7일로 잡는다.

## 제외 영역과 이유

- **못 먹는 음식 제외 조건** — 사용자 입력형 제외 조건은 현재 제품 범위에 포함하지 않는다. 실측에서도 카카오 장소 데이터에 재료 정보가 없어 실제 알레르겐을 걸러낼 수 없고, 입력창을 두면 잘못된 안전감을 줄 수 있음이 확인됐다. 근거: `PRODUCT.md`, `docs/research/phase0-kakao-category-analysis.md`.
- **초기 취향조사(30초 A/B 설문), Food Profile/Food Type** — 브리프에서 "시간이 남으면" 항목으로 이미 표시됨. 개인화 학습 자체가 이번 범위 밖이라 초기값을 만들 대상이 없다.
- **그룹 저장(자주 만나는 조합 재사용)** — 하루 강의 MVP 목록에 없음. 참가자 구성 자체는 있지만 재사용 저장은 다음 단계로 미룬다.
- **정교한 다양성 추천(슬롯 구성, 카테고리 최소/최대 제약, 최근성 패널티)** — 브리프에서도 "시간이 남으면" 항목. 이번 규칙은 최근 방문 제외 정도로 단순화했다.
- **그룹 궁합/Food Profile 궁합 화면** — 개인화 데이터가 없는 이번 범위에서는 만들 수 없다.
- **게스트(비가입자) 참가자** — `PRODUCT.md`에 아직 열린 질문으로 남아 있다. 이번 스펙은 오늘 참가자 전원이 가입자라고 전제한다.
- **자동 preference learning, population(연령대·성별) 가중치** — 연령대·성별은 가입 시 수집하지만 이번 범위의 후보 추천에는 사용하지 않는다. 이번 범위는 학습 없는 고정 규칙만 쓰며, 해당 추천 시스템을 도입한 뒤 별도의 추천 품질 검증 테스트를 추가한다.
- **식후 평가("또 갈래/별로")** — 브리프의 MVP 목록은 "최종 결과 저장, 과거 선택 조회"까지만 명시했고 식후 평가는 언급하지 않았다. 평가 데이터가 쌓여야 의미 있는 preference learning과 함께 다음 단계로 미룬다.

## 보류된 사항

- 게스트 참가자 허용 여부(`PRODUCT.md` Unknown) — 이번 스펙은 관여하지 않는다.
- 샤브샤브·뷔페·도시락·퓨전요리·패밀리레스토랑·패스트푸드의 포함 여부(`docs/decisions/food-category-taxonomy.md` Boundaries) — 이번 스펙의 필터는 이 카테고리들을 제외하지 않고 그대로 남겨둔다.

## 남은 위험

- 카카오 카테고리 검색은 중심점당 최대 45건까지만 반환한다(API 자체 상한, 실측 확인). 음식점이 밀집한 지역에서도 "반경 내 전체"가 아니라 "가장 가까운 45곳"에서만 후보가 만들어진다. 홍대입구는 반경 1km에 음식점이 2,537곳 있지만 그중 45곳만 후보 풀이 된다.
- 거리순으로 조회하면 실효 탐색 범위가 130~145m로 좁아진다. 즉 `radius=1km`는 저밀도 지역에서만 실제로 작동하는 상한이고, 도심에서는 사실상 아무 역할도 하지 않는다. 나중에 반경을 조정해도 도심에서는 결과가 변하지 않는다.
- "최근 7일 내 방문 제외" 규칙은 결과 저장 이력이 없는 첫 사용에서는 아무 효과가 없다. 이 필터가 작동하는 모습을 보여주려면 사전에 결과가 한 번 이상 저장되어 있어야 한다.
- 승자 유지 방식은 등장 순서가 뒤인 후보에게 유리하다. 8개면 첫 자리 후보는 7번 이겨야 하지만 마지막 자리는 1번만 이기면 된다. 시작 시 순서를 무작위로 섞어 기대값은 공평하게 만들지만, 개별 세션에서는 편향이 남는다.
- PIN 기반 인증은 무차별 대입에 약할 수 있다. 강의용 데모 스코프에서는 수용하되, 실제 서비스라면 재검토가 필요하다.
- 카카오 REST 키는 브라우저에 노출되면 안 된다. 조회는 서버 경유로만 이루어져야 한다.
